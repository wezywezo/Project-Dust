**Statut :** Vivant (évolue avec le projet)

---

# Qu'est-ce que Project Dust ?

Project Dust est un moteur de jeu conçu pour servir d'intermédiaire entre un joueur, une intelligence artificielle et les règles de **Fallout 2d20**.

Son rôle est de garantir la cohérence des règles, de maintenir l'état du monde et de coordonner les différents modules qui composent le système afin d'offrir une expérience de jeu immersive, fluide et fiable.

Project Dust ne remplace ni le joueur ni l'intelligence artificielle.

Il leur permet de se concentrer sur ce qu'ils font le mieux.

---

# Notre mission

Project Dust a une mission simple.

Permettre au joueur de vivre une expérience de jeu de rôle immersive avec une intelligence artificielle sans avoir à se préoccuper des règles.

Pour y parvenir :

- le joueur prend les décisions et interprète son personnage ;
- l'intelligence artificielle raconte l'histoire, anime le monde et incarne les personnages ;
- Project Dust applique les règles, garantit la cohérence et maintient l'état du monde.

Le moteur n'est pas le produit.

Il est le facilitateur de cette expérience.

---

# Notre vision

Nous souhaitons que les règles deviennent presque invisibles.

Le joueur ne devrait pas avoir à consulter un manuel.

L'intelligence artificielle ne devrait pas avoir à mémoriser l'ensemble des mécaniques d'un système de jeu.

Project Dust prend en charge cette responsabilité afin que chacun puisse se concentrer sur ce qu'il fait le mieux.

Notre ambition n'est pas seulement de créer un moteur de jeu.

Nous voulons concevoir une nouvelle manière de faire collaborer un joueur, une intelligence artificielle et un système de règles.

---

# Nos valeurs

Nous privilégions toujours :

- la compréhension avant l'implémentation ;
- la simplicité avant la complexité ;
- les besoins réels avant les besoins hypothétiques ;
- la qualité avant la rapidité ;
- une source de vérité unique plutôt que la duplication des informations ;
- les décisions réfléchies plutôt que les solutions improvisées.

Nous acceptons de réécrire le code.

Nous refusons de perdre le raisonnement qui a conduit à son écriture.

---

# Notre philosophie de développement

Nous développons uniquement ce dont le projet a réellement besoin.

Avant d'introduire une nouvelle abstraction, une architecture complexe ou une nouvelle technologie, nous nous posons toujours les questions suivantes :

- Project Dust en a-t-il réellement besoin aujourd'hui ?
- Quel problème concret cette solution résout-elle ?
- Existe-t-il une solution plus simple ?
- Que perdons-nous si nous ne faisons rien maintenant ?

La simplicité est un choix d'ingénierie.

Nous appliquons le principe **YAGNI (You Aren't Gonna Need It)**.

Nous préférons faire évoluer une architecture au rythme du projet plutôt que de tenter de prévoir tous ses besoins futurs.

---

# Notre philosophie d'apprentissage

Project Dust est également un projet d'apprentissage.

Chaque décision est une occasion de mieux comprendre le développement logiciel, la conception d'architecture et les systèmes de jeu.

Nous ne cherchons pas à accumuler des connaissances.

Nous cherchons à comprendre pourquoi elles existent, dans quelles situations elles apportent de la valeur et quand il est préférable de ne pas les utiliser.

L'apprentissage accompagne le projet.

Il n'en remplace jamais la mission.

---

# La règle du café ☕

Lorsque nous avons l'impression de foncer vers une solution...

Nous nous arrêtons.

Nous discutons.

Nous remettons nos hypothèses en question.

Puis seulement nous reprenons le développement.

Réfléchir fait partie du développement.

# Les fondations du projet

Les documents de fondation définissent la vision, les principes et la manière de développer Project Dust.

Ils constituent le cadre de référence du projet.

Ils n'évoluent que lorsqu'une expérience concrète démontre qu'un principe fondamental doit être revu.

La stabilité des fondations permet au projet d'évoluer sans remettre constamment en question ses bases.

---

# Nos principes fondateurs

- La mission guide l'architecture.
- La simplicité est une force.
- Les connaissances ont plus de valeur que le code.
- Les décisions importantes doivent pouvoir être expliquées.
- Documenter le **pourquoi** est souvent plus important que documenter le **comment**.
- Chaque fonctionnalité doit résoudre un problème réel.
- Le code est temporaire.
- Les principes durent.
- La documentation décrit la réalité du projet, pas des hypothèses.
- Un projet réussi est un projet que l'on peut comprendre, reprendre et faire évoluer plusieurs années plus tard.

---

# Notre engagement

Chaque sprint doit améliorer trois choses :

- le projet ;
- l'expérience qu'il offre ;
- les connaissances de ceux qui le développent.

Nous acceptons que notre implémentation évolue.

Nous protégeons les principes qui guident cette évolution.
